# この PR が追加するもの: ヘッドレス実行のためのライブアクティビティ表示

この PR はマルチハーネス対応（`feature-otherharness`）の上に積むスタック構成で、
その一部 — ヘッドレスの `optimize` 実行中にターミナルに何を表示するか — を改良します。

`cclens optimize --harness opencode` は opencode 自身のエージェントをヘッドレスで
起動し、解析結果を渡します。ターミナルは設計上静かです。ナレーションと計画は stdout
へ、生の出力は非公開のログへ。静かな実行でも静かな時間帯には 30 秒ごとに薄い
ハートビート行が出るので、完全に止まって見えることはありません。ただし 30 秒は沈黙を
眺めるには長く、ハートビートはアドバイザが**今何をしているか**を何も語りません。

## 変更するもの

ハートビートを **1 行のインプレース・ステータス行**に置き換えます。Claude Code の
アクティビティスピナーをモデルにしたものです。

- 回転する点字スピナーが生存を示します。フレームは 100ms ごとに回る — 生きて見える
  素早さで、スクリーンショットしてもきれいな字形が残る素早さです。
- ステータスは**今の作業**を最後のツールイベントから名前付けます。"running shell"、
  "reading"、"searching"、"spawning subagent"、"planning"、テキスト出力の後は
  "thinking"。未知のツールは推測ではなく "running \<name\>" と正直に。
- 経過カウンタ（`(42s)`）が待ち時間を測定可能にします。

```text
⠸ advisor working — running shell (42s)
```

## なぜインプレースか、なぜパイプのフォールバックが重要か

- ターミナル上では同じ行を書き換えて流れません（`\r` + `ESC[2K`）。長い実行で画面が
  氾濫しません。再描画はクリア処理と共有ロックを持つので、再描画の間に出力される
  ナレーションがステータス行に干渉しません。
- stderr がパイプのとき、ANSI の書き換えはストリームを壊します。同じ拍を 10 秒ごとの
  改行ログにフォールバックさせ（`… advisor working — running shell (42s, 41 events)`）、
  ツールごとの進捗マーカーは行として出力します。パイプにエスケープコードが混ざる
  ことはありません。
- **stdout** をパイプしてもスピナーは生きています。`optimize | pbcopy` では pbcopy が
  ナレーションと計画だけを受け取る間、ターミナルにはステータス行が表示され続けます。
- テキスト出力の前に必ず行をクリアするので、ナレーションがスピナーの上に印刷される
  ことはありません。
- `NO_COLOR` と `TERM=dumb` を尊重します。エラー終了でも `Drop` 経由で停止するので、
  失敗した起動がスレッドや古い行を残しません。

## 変更しないもの

- すべての生イベントは今までどおり実行ログへ。indicator が決めるのはターミナルに
  何を出すかだけです。
- 10 秒ごとの改行拍はパイプされた stderr で何も置き換えません。そこでも静かな
  時間帯はカバーされ、「停止ではなく待機中」という保証は同じです。
- `--verbose` は今までどおり生ストリームの stdio を継承します。

## 検証方法

- ユニットテストがスピナーフレームの回転、アクティビティラベルの対応、ステータス行の
  形式、共有状態の詳細をカバーします。
- ゲート全体が通ります。`cargo fmt --check`、`cargo clippy --all-targets
  --all-features -- -D warnings`、`cargo test` — **304 テスト**。
- 実際の opencode ストア（91 セッション）で実行しました。ターミナル上ではステータス行
  がインプレースで書き換わり、stderr をパイプすると改行拍にフォールバックし、
  `| pbcopy` にはナレーションと計画だけが入ります。
